## 🎯 Project Overview

The **Sumit Panchal QA Portfolio** is a professional portfolio website developed to showcase my experience as a Manual QA Engineer, testing knowledge, professional skills, and practical work.

The project combines a responsive React frontend with a Node.js and Express backend, MongoDB database integration, administrator authentication, blog management, and Cloudinary-based image management.

The portfolio also includes an administrator panel that allows authorized users to manage blog content and related resources through protected backend APIs.

### 🌟 Project Objectives

- Present my professional experience and Manual QA expertise.
- Showcase projects, testing skills, and quality assurance practices.
- Provide a responsive and accessible portfolio experience.
- Support administrator-controlled blog management.
- Store blog and administrator data using MongoDB.
- Manage uploaded images through Cloudinary.
- Maintain a reliable frontend and backend deployment architecture.

## 🔐 JWT Authentication & Administrator Workflow

Administrator functionality is protected by authentication and authorization controls.

```text
Administrator
      |
      |
   Login
      |
      |

      |
      |

      |

      |
      |

|             |              |
Profile    Blog Management  Password

```

### Administrator Capabilities

- Login to the administrator panel.
- Access protected administrator functionality.
- View administrator profile information.
- Change the administrator password.
- Create blog posts.
- Edit existing blog posts.
- Delete blog posts.
- Upload blog images through the protected upload endpoint.
- Receive feedback during image validation and upload operations.

### Security Considerations

- Administrator APIs must verify authentication.
- Passwords must be stored using secure hashing.
- JWT secrets must remain in backend environment variables.
- Protected operations should not be available to unauthenticated users.
- Authentication errors should be handled appropriately.

### 🆕 Recent Admin Panel Updates

The latest documented improvements focus on making blog image handling more reliable and improving feedback inside the administrator workflow.

| Area | Recent Update | Benefit |
|---|---|---|
| Image Validation | Added file-type and file-size validation before upload. | Prevents unsupported or oversized files from reaching the backend. |
| Large Image Warning | Displays a warning toast when the original image exceeds 10 MB. | Informs administrators that image processing may take longer. |
| Image Compression | Resizes images to a maximum width of 1920 pixels and converts them to JPEG at quality 0.75. | Reduces upload size while preparing images for storage. |
| Admin Image Upload | Uses the authenticated `POST /api/blogs/upload` endpoint. | Restricts image uploads to authorized administrators. |
| Upload Progress | Displays upload progress in the frontend. | Provides feedback while an image is being uploaded. |
| Backend Upload Handling | Uses Multer memory storage and processes the uploaded image buffer. | Avoids depending on a permanent local upload directory. |
| Cloudinary Integration | Uploads processed image data to Cloudinary. | Provides hosted image URLs for blog content. |
| Upload Timeout | Uses a five-minute timeout for the relevant upload request and backend handling. | Allows more time for large uploads and slower network conditions. |
| Upload Response Validation | Checks that the returned Cloudinary image URL uses HTTPS. | Helps prevent invalid image URLs from being accepted. |

**Important:** The warning for images larger than 10 MB is informational and does not automatically block the compression workflow.

## 🖼️ Cloudinary Image Management

Cloudinary is used for hosted image storage and delivery.

The administrator can upload blog images through the protected backend upload endpoint.

### Image Upload Architecture

```text
Administrator Selects Image
          |
          |
Frontend File Validation
          |
          |
Image Resizing and Conversion
          |
          |
Multipart Upload Request
          |
          |
JWT Authentication
          |
          |
Multer Memory Storage
          |
          |
Image Buffer Processing
          |
          |
Cloudinary Upload
          |
          |
Cloudinary HTTPS Image URL
          |
          |
Blog Content Uses Image URL
```

### Frontend Image Processing

The frontend image utility is:

```text
src/services/imageUtils.js
```

The documented image-processing rules are:

| Setting | Current Behaviour |
|---|---|
| Accepted original formats | JPEG, PNG, WebP, GIF |
| Maximum original file size | 50 MB |
| Warning threshold | More than 10 MB |
| Maximum output width | 1920 pixels |
| Output format | JPEG |
| JPEG quality | 0.75 |

**GIF consideration:** GIF files may be accepted as original input, but the conversion process produces JPEG output. Animated GIF frames are therefore not preserved.

### Backend Image Upload

The backend upload middleware is:

```text
backend/src/middlewares/uploadBlogImage.js
```

The middleware uses **Multer Memory Storage** rather than CloudinaryStorage.

The upload route is:

```http
POST /api/blogs/upload
```

The request is protected by administrator authentication and uses multipart form data.

| Backend Setting | Value |
|---|---|
| Storage method | Memory Storage |
| Maximum backend file size | 5 MiB |
| Maximum files | 1 |
| Maximum fields | 10 |
| Maximum multipart parts | 11 |
| Accepted MIME types | JPEG, PNG, WebP |
| File validation | MIME type and binary signature validation |

The upload flow processes the image buffer and sends it to Cloudinary. The resulting Cloudinary URL is returned to the frontend.

### Cloudinary Environment Variables

Configure the following variables in the backend environment:

```env
CLOUDINARY_CLOUD_NAME=your_cloudinary_cloud_name
CLOUDINARY_API_KEY=your_cloudinary_api_key
CLOUDINARY_API_SECRET=your_cloudinary_api_secret
```

Never commit real Cloudinary credentials to GitHub or include them in public documentation.

### Cloudinary Health Check

```http
GET /api/cloudinary-health
```

Production endpoint:

https://sumit-panchal-qa-portfolio-1h3z.onrender.com/api/cloudinary-health

### Image Persistence

The application stores uploaded image assets through Cloudinary rather than relying on a permanent local backend upload folder.

The blog record stores the resulting image reference.

Image availability depends on the Cloudinary account, asset status, configuration, and retention of the corresponding Cloudinary resource.

## ⚙️ Getting Started

Follow these steps to run the project locally.

### Prerequisites

Install the following tools:

- Node.js
- npm
- Git
- MongoDB connection or MongoDB Atlas account
- Cloudinary account for image uploads

### 1. Clone the Repository

```bash
git clone https://github.com/lifeofthecoders/Sumit-Panchal-QA-Portfolio.git
```

Navigate into the project:

```bash
cd Sumit-Panchal-QA-Portfolio
```

### 2. Install Frontend Dependencies

From the project root:

```bash
npm install
```

### 3. Install Backend Dependencies

```bash
cd backend
npm install
```

### 4. Configure Backend Environment Variables

Create a `.env` file inside the `backend` directory.

```env
PORT=5000
NODE_ENV=development

MONGODB_URI=your_mongodb_connection_string
LOCAL_MONGODB_URI=mongodb://127.0.0.1:27017/qa_portfolio

JWT_SECRET=your_long_random_secret_at_least_32_characters

CORS_ORIGIN=http://localhost:5173,https://lifeofthecoders.github.io

CLOUDINARY_CLOUD_NAME=your_cloudinary_cloud_name
CLOUDINARY_API_KEY=your_cloudinary_api_key
CLOUDINARY_API_SECRET=your_cloudinary_api_secret
```

Add any other environment variables required by the backend configuration, including email-related settings if those features are enabled.

Do not use the example placeholders as production credentials.

### 5. Start the Backend

From the `backend` directory:

```bash
npm run dev
```

The backend should be available at:

```text
http://localhost:5000
```

### 6. Start the Frontend

Open another terminal and navigate to the project root:

```bash
npm run dev
```

The Vite development server typically runs at:

```text
http://localhost:5173
```

### 7. Create a Production Build

From the project root:

```bash
npm run build
```

The production build is generated in the `dist` directory.

## 🔌 API Overview

The backend exposes REST API endpoints for health checks, administrator operations, and blog management.

### Health Endpoints

| Method | Endpoint | Purpose |
|---|---|---|
| GET | `/` | Backend root response |
| GET | `/api/health` | Backend health verification |
| GET | `/api/cloudinary-health` | Cloudinary configuration and connectivity check |

### Administrator Operations

The administrator authentication and management routes support the following operations:

| Operation | Purpose |
|---|---|
| Login | Authenticate an administrator |
| Profile | Retrieve administrator profile information |
| Change Password | Change administrator credentials |
| Logout | Handle administrator logout |

The exact route paths are defined in the backend administrator route configuration.

### Blog Operations

| Method | Endpoint | Purpose |
|---|---|---|
| GET | `/api/blogs` | Retrieve blog posts |
| GET | `/api/blogs/:id` | Retrieve a specific blog post |
| POST | `/api/blogs` | Create a blog post |
| PUT | `/api/blogs/:id` | Update a blog post |
| DELETE | `/api/blogs/:id` | Delete a blog post |
| POST | `/api/blogs/upload` | Upload a blog image to Cloudinary |

**Image upload request details:**

- Authentication: Administrator JWT required.
- Content type: `multipart/form-data`.
- File field: `image`.
- Backend file limit: 5 MiB.
- Successful upload: Returns the hosted image URL.

## 🛡️ Security & Configuration Practices

The project uses environment-based configuration and protected backend operations.

### Security Practices

- Keep database connection strings private.
- Store JWT secrets in backend environment variables.
- Never expose Cloudinary API secrets in frontend code.
- Never commit `.env` files.
- Use `.gitignore` to exclude sensitive configuration files.
- Protect administrator APIs through authentication.
- Validate image file types and signatures.
- Apply file-size and multipart request limits.
- Use HTTPS for production communication.
- Avoid storing unnecessary sensitive information in logs.

### Environment Configuration

Example environment files may use placeholders, but production secrets must be configured through the hosting provider's environment settings.

### Important

If an actual API key or secret has ever been committed to a public repository or shared publicly, rotate it through the corresponding service provider.
